# AI-Driven Network Traffic Analysis and Intrusion Detection System

A hybrid network intrusion detection system that reads labelled connection records
or raw packet captures, extracts 55 behavioural features, scores every flow through
three independent detection layers, and emits a ranked alert queue in which **every
alert carries the evidence that produced it** — the rule that fired, the feature
values that drove the classifier, the anomaly percentile, and a fused confidence.

Everything under `nids/` is written from scratch on NumPy: the CART trees, the
random forest, the isolation forest, the feature extractor, the pcap parser and the
fusion logic. There is no scikit-learn, scapy or dpkt in the detection path.

## Read this first: where the numbers come from

Every metric quoted in this repository, in `docs/REPORT.md` and on the slides was
measured on the **real NSL-KDD benchmark** — `KDDTrain+.txt` (125,973 connection
records) fitted, `KDDTest+.txt` (22,544 records) scored, with the official
train/test split left untouched. No row of the test file is seen during fitting,
and no threshold is tuned on it.

The banner printed by every command states which corpus is in use, and refuses to
be subtle about it either way:

```
corpus    : NSL-KDD (KDDTrain+ / KDDTest+)  [real]
Real benchmark files found in data/raw and used as-is.
```

If the two files are absent, `--source nsl-kdd` falls back to a seeded simulator
(`nids/data/simulate.py`) that reproduces NSL-KDD's schema, class mix and
train/test family shift, so a reviewer with no network access can still run the
whole pipeline. In that case the banner shouts about it:

```
corpus    : SIMULATED NSL-KDD-schema corpus  [simulated]
Real KDDTrain+.txt / KDDTest+.txt were not found in data/raw.

!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
!! SIMULATED CORPUS. Every number below is generated by
!! nids/data/simulate.py and is NOT an NSL-KDD benchmark result.
!! Put KDDTrain+.txt and KDDTest+.txt in data/raw/ and re-run.
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
```

Numbers from a simulated run are not benchmark numbers and must not be cited as
such. Nothing in the code branches on which corpus is loaded — the fallback exists
so the prototype always runs, not so the results can be quoted either way.

## Quickstart

```bash
git clone <this-repo> && cd ai-nids
python -m pip install -r requirements.txt

python scripts/run_all.py          # ~6 min: dataset -> 131 tests -> train -> evaluate
                                   #         -> scenarios -> figures -> dashboard
open artifacts/dashboard.html      # self-contained; no server, no CDN
```

`run_all.py` is the single reproduction command. It fails on the first non-zero
step rather than building a report on top of a broken learner, and it prints a
timing table at the end. Add `--quick` for a 30-tree smoke test (do not quote
numbers from a `--quick` run) or `--skip-tests` to skip the suite. Roughly half
the six minutes is fitting the two forests on 125,973 rows; the isolation forest
alone is about 90 s of it.

Requirements: Python 3.10+, and the four packages in `requirements.txt` (numpy,
pandas, matplotlib, jinja2). Node.js is optional — if present, `run_all.py` also
executes the dashboard's own JavaScript headlessly. Built and tested on Python
3.10.12 with numpy 2.2.6, pandas 2.3.3, matplotlib 3.10.9.

## Getting traffic data

Four sources are supported, selected with `--source`. Everything runs with no
downloads at all, so a reviewer is never blocked.

**1. NSL-KDD (default, recommended).** Place `KDDTrain+.txt` and `KDDTest+.txt`
in `data/raw/`, or let the helper try the known mirrors:

```bash
python scripts/fetch_nsl_kdd.py            # download into data/raw/
python scripts/fetch_nsl_kdd.py --check    # just report what is present
```

If every mirror is unreachable the script prints manual instructions and exits
non-zero instead of pretending to have succeeded. By hand: download
`NSL-KDD.zip` from the Canadian Institute for Cybersecurity
(<https://www.unb.ca/cic/datasets/nsl.html>), unzip it, and copy `KDDTrain+.txt`
and `KDDTest+.txt` into `data/raw/`. The corpus is not vendored into git — it is
redistributed under UNB's terms and a 20 MB dataset does not belong in source
control.

NSL-KDD is the right corpus for this brief: it labels all four required traffic
classes (benign, `probe` reconnaissance, `dos` flooding, and `r2l`/`u2r` as the
additional attack types), and its test split deliberately contains attack families
absent from training — a built-in zero-day proxy that scenario 5 exploits.

`python -m nids data` prints the mix it is actually using. On the real corpus:

| split | rows | normal | dos | probe | r2l | u2r |
|---|---|---|---|---|---|---|
| train | 125,973 | 67,343 | 45,927 | 11,656 | 995 | 52 |
| test | 22,544 | 9,711 | 7,458 | 2,421 | 2,887 | 67 |

The shift between those two rows is the point, not an accident: `r2l` is 0.79% of
training and 12.8% of test, `u2r` has 52 training examples in 125,973, and 17 test
families never appear in training at all (`apache2`, `httptunnel`, `mailbomb`,
`mscan`, `named`, `processtable`, `ps`, `saint`, `sendmail`, `snmpgetattack`,
`snmpguess`, `sqlattack`, `udpstorm`, `worm`, `xlock`, `xsnoop`, `xterm`) — 3,750
test connections, 16.6% of the file and 29.2% of its attacks. A detector that only
interpolates its training distribution cannot do well here, which is exactly what
scenario 5 measures.

**2. Simulated (automatic fallback).** No files, no flags: if the NSL-KDD files
are missing, `--source nsl-kdd` falls back to `nids/data/simulate.py` and says so
loudly. Seeded, so two runs on the same seed agree exactly.

**3. CICIDS2017 (optional secondary corpus).** Point `--source cicids` at the
`MachineLearningCVE/*.csv` flow exports in `data/raw/cicids/`. Provided to show the
feature extractor is not welded to one schema; the reported results are not from it.

**4. Raw packet capture.** The packet path takes classic pcap bytes and builds
flows itself with `struct` — no capture library:

```bash
python scripts/make_demo_pcap.py                    # -> data/raw/demo_capture.pcap
python -m nids detect --source pcap --pcap data/raw/demo_capture.pcap --limit 10
```

The demo capture is synthesised (real Ethernet/IPv4/TCP/UDP/ICMP headers, four
labelled phases: benign HTTP+DNS, a SYN port scan, a SYN flood, an ICMP sweep) and
opens in Wireshark as a normal file. It is a fixture that proves
`packets -> flows -> features -> alerts` works on real bytes; it is not evidence
about accuracy. Any capture you own works in its place.

## How it works

```
corpus / pcap ──▶ feature extraction ──▶ ┌ signature rules R01–R12 ┐
   55 features      2-s trailing window   │ supervised forest (120) │──▶ fusion ──▶ ranked
   per flow         + last-100-conn block │ isolation forest (150)  │    + explain    alerts
                    + 14 derived rates    └─────────────────────────┘
```

**Feature extraction** (`nids/features.py`) produces 55 features per flow in three
blocks. The native numeric columns cover basic volumetrics (duration, byte counts
each way), content flags (failed logins, root access, `su_attempted`), a 2-second
trailing traffic window (connection rate, same-service and same-host rates, SYN and
REJ error rates) and a last-100-connections destination-host block. On top of those
sit 14 derived quantities — `log_src_bytes`, `log_dst_bytes`, `byte_ratio`,
`bytes_per_second`, `conn_per_second`, `error_pressure`, `service_entropy_proxy`,
`auth_pressure`, `service_freq` and the protocol/flag indicators — because rate and
asymmetry, not raw counts, are what separate a flood from a busy server. Three
ordinal-encoded categoricals (`protocol_type`, `service`, `flag`) finish the vector,
with a reserved code for values unseen in training.

**Layer 1, signature rules** (`nids/detect/signatures.py`): 12 hand-written rules
over named features, each carrying a human-readable reason string. Cheap,
interpretable, and the only layer that can name a technique. Eight of the twelve run
at ≥0.92 precision on the test split; R09 (5 fires, 0.400) and R04 (100 fires,
0.480) do not, and are reported that way rather than tuned away.

**Layer 2, supervised random forest** (`nids/ml/forest.py`): 120 histogram-binned
CART trees, bootstrap sampling, balanced class weights, out-of-bag score 0.9989.
Explanations are exact additive contributions in the treeinterpreter style — the
bias plus the per-feature contributions reconstruct `predict_proba` to the last
digit, so the explanation is the model, not a post-hoc story about it.

**Layer 3, isolation forest** (`nids/ml/iforest.py`): 150 trees fitted on the 67,343
benign training rows only, scoring `2^(-E[h(x)]/c(ψ))`. The alert threshold is the
99th percentile of benign novelty (0.5737), which makes the reported confidence a
rank statistic against normal traffic rather than an arbitrary cut.

**Fusion** (`nids/detect/hybrid.py`) — *detection is a union, priority is a
product.* A noisy-OR over weighted layer votes (signature 1.00, supervised 0.90,
anomaly 0.60) decides the confidence, then a single-layer corroboration discount
(0.62 / 0.55 / 0.45) demotes alerts only one layer believes. Nothing is ever
suppressed; uncorroborated findings still reach the queue, just lower. Severity
bands: ≥0.85 critical, ≥0.65 high, ≥0.45 medium, else low.

**Explainability** (`nids/detect/explain.py`): every alert records what was
flagged, which layers fired and why, the top signed feature contributions with
their actual values, the anomaly percentile, the fused confidence and the severity
band. A bare label is never emitted.

## Using it

```
python -m nids <command> [options]

  data         show which corpora are available and their mix
  train        fit the three layers and save the detector
  detect       run detection and show explained alerts
  evaluate     full metric suite -> artifacts/evaluation.json
  scenarios    the five mandatory demonstrations
  dashboard    render the self-contained HTML view
  all          train, evaluate, scenarios, figures, dashboard
```

Options shared by every command: `--source {nsl-kdd,simulated,cicids,pcap}`,
`--pcap PATH`, `--max-packets N`, `--max-rows N`, `--model PATH`, `--seed N`,
`--quiet` (drop the provenance banner), `--no-colour`.

```bash
# what data do I actually have?
python -m nids data

# fit and save the detector (--trees / --iforest control forest sizes)
python -m nids train --trees 120 --iforest 150

# the five most severe alerts, with full evidence for each
python -m nids detect --limit 5 --detail 1 --min-severity critical

# filter the queue; --json writes the alerts for downstream tooling
python -m nids detect --category probe --limit 20 --brief
python -m nids detect --summary-only
python -m nids detect --json artifacts/alerts/queue.json

# precision / recall / accuracy, ROC-AUC, the ablation, TP+FP+FN worked examples
python -m nids evaluate --examples 3

# the mandatory scenarios, individually or all at once
python -m nids scenarios --only 1 2      # baseline + reconnaissance
python -m nids scenarios --only 3        # DoS, and what it does to the metrics
python -m nids scenarios --only 4        # additional attack types (r2l / u2r)
python -m nids scenarios --only 5        # the borderline / missed case
python -m nids scenarios                 # all of them, + the pcap scenario

# rebuild the nine figures and the HTML dashboard
python -m nids dashboard --top 200
```

**Choosing the traffic data** is a flag, per the brief's "user selects the traffic
data" requirement: `--source` picks the corpus, `--pcap` picks a capture file, and
`--max-rows` / `--max-packets` bound the volume. The prototype's own view of the
selection is printed as a provenance banner before any detection happens.

**The dashboard** (`artifacts/dashboard.html`) is a single self-contained file —
inline CSS and JS, base64 figures, no server and no CDN. It carries the alert queue
with per-alert evidence panels, severity filters, the metric tables, the ablation,
the nine figures and the six scenario write-ups. Open it directly in a browser.

## Results

Real NSL-KDD, 125,973 train / 22,544 test (9,711 benign, 12,833 attack).
Reproduce with `python -m nids evaluate`; the full JSON is
`artifacts/evaluation.json`.

| detector | precision | recall | F1 | FPR |
|---|---|---|---|---|
| signatures only | 0.9700 | 0.5918 | 0.7351 | 0.0242 |
| supervised forest only | 0.9664 | 0.6433 | 0.7725 | 0.0296 |
| anomaly layer only | 0.9807 | 0.6033 | 0.7470 | 0.0157 |
| signatures ∨ supervised | 0.9607 | 0.7335 | 0.8319 | 0.0396 |
| signatures ∨ anomaly | 0.9662 | 0.6893 | 0.8046 | 0.0318 |
| **hybrid (all three)** | **0.9599** | **0.7707** | **0.8549** | **0.0425** |

Binary accuracy 0.8511 (TP 9,890, FP 413, FN 2,943, TN 9,298); multiclass accuracy
0.7660, macro-F1 0.5646. ROC-AUC: supervised 0.9695, anomaly 0.9417, fused hybrid
score 0.8704 — the fused score is a *priority* ranking, not a calibrated
probability, and the corroboration discount that makes it useful as a queue order is
exactly what costs it AUC against the raw model scores. Queue of 10,303 alerts
(45.70% alert rate); precision@k is 1.000 out to k=2,000. Throughput 833.3 rows/s
single-threaded, of which the anomaly layer is 24.52 s of the 26.96 s detection
total. Timings are the one machine-dependent figure here; every other number above
is seeded and reproduces exactly.

**The honest read of that table.** Each layer alone lands in a narrow band
(F1 0.735–0.773) and every pairing beats every single layer, so the fusion is doing
what it was built to do: the hybrid gains +0.120 F1 over signatures alone and
+0.082 over the forest alone, mostly as recall (+0.179 and +0.127). The
third layer is not free but it is not decoration either — going from
`signatures ∨ supervised` to the full hybrid converts 477 missed attacks into
detections for 28 extra false positives, +0.037 recall and +0.023 F1 at a cost of
+0.003 FPR. That is the best marginal trade in the table, and it comes from the one
layer that needs no labels at all.

The cost is concentrated where a single-layer design would hide it. All three layers
are individually precise (≥0.966), yet the union's 413 false positives spread across
every layer rather than one bad component: 287 involve the supervised forest, 235 the
rules, 152 the anomaly layer, and **187 of the 413 are corroborated by two or more
layers** — including 74 on which all three agree. Corroboration raises the odds an
alert is real; it does not make it real, and 173 of these false positives are ranked
`critical` for exactly that reason. Among the rules, the false positives concentrate
in R06 (113 benign fires), R04 (52), R10 (43) and R11 (19).

**Per-scenario headlines** (`python -m nids scenarios`, full JSON in
`artifacts/scenarios.json`):

| # | scenario | result |
|---|---|---|
| 1 | benign baseline | FPR 0.0425 — **not** a clean sheet; 413 of 9,711 benign flows raise something, about 1 in 24 |
| 2 | reconnaissance / port scan | recall 0.9839 at precision 1.000; `ipsweep`, `nmap`, `portsweep`, `satan` all 1.000 |
| 3 | DoS flood | recall 0.9025 at precision 1.000; 6,731 alerts = 65.3% of the queue from 169 distinct signatures (≈40 alerts each) |
| 4 | r2l + u2r | recall 0.263 (r2l 0.2553, u2r 0.597); fusion adds loadmodule +1.000, sqlattack +1.000, buffer_overflow +0.600 over the forest alone |
| 5 | unseen families | seen 0.8305 vs unseen 0.6259 — a **0.2046 generalisation gap**; `snmpguess` scores 0.000 on all three layers across 331 rows |
| 6 | pcap path | 755 flows in ~0.97 s; benign host 0/90 alerts, port scanner 30/30 with R06+R07, SYN flood 595/595 with R01, ICMP sweep 40/40 but rule-less and ranked `low` |

Scenario 1 does not pass the brief's "no false alarms" bar and the discussion says
so. Scenario 3 shows the flood's real operational cost: it is not a metric problem
but a queue problem — `neptune` alone is 4,656 alerts, 45.2% of everything an analyst
would see. Scenario 4 is where this system is weakest by a wide margin: 0.263 recall
on the credential-and-escalation classes, driven by `guess_passwd` at 0.008 over
1,231 connections, and the reason is visible in the features rather than in the
hyperparameters — a successful password guess is one short authenticated session that
looks like every other login. Scenario 5 quantifies what leaning on a supervised
layer costs: 0.6259 recall on the 3,750 test connections whose family never appears
in training.

**Worked examples** are extracted automatically by `evaluate` — a true positive
(row 12047, `satan`, confidence 1.00, all three layers agreeing, correctly flagged
but mis-attributed to `dos` because R01 outranks R06), a false positive (row 476, a
genuinely benign `private`/`rstr` flow with `count=143`, flagged `probe` at 0.994 by
R06+R07 *and* corroborated by both models — the forest puts `probe` at 1.000 and the
anomaly layer at the 99.95th percentile of benign traffic, which is why corroboration
is not a safety net), and a false negative (row 2534, an `imap4` session where no
layer fired: the forest called it `normal` at 0.659 and the anomaly score landed at
0.5737, on the threshold rather than above it). Across all 2,943 false negatives the
pattern is not near-misses — the median supervised attack probability is 0.133 and
the median anomaly novelty 0.7465, far below the 0.99 line. The system is not
hesitating on these; it is confidently wrong.

## Network and security considerations

**Inline performance.** 833.3 rows/s single-threaded, and the anomaly layer is 91%
of that budget (24.52 s of 26.96 s). For a mirrored 1 Gbps link this is an
out-of-band analytic, not an inline blocker. The forests are embarrassingly
parallel, so the fix is process-level sharding rather than an algorithmic one.

**Capture reliability.** The extractor works on assembled flows, so anything that
prevents assembly is a blind spot before detection begins: dropped frames under
load, unidirectional taps that hide the response direction, truncated snaplen that
loses payload flags, and asymmetric routing that splits a conversation across
sensors. The pcap reader rejects pcapng and truncated files loudly (with a
conversion hint) instead of quietly producing partial flows.

**Evasion.** Every rule is a threshold over a rate, so slowing an attack under the
2-second window defeats it directly — a scan at one probe per 30 s never reaches
R06's same-host count. The supervised layer inherits its training distribution and
loses 0.2046 recall on families it has not seen. The anomaly layer's threshold is a
benign percentile, so poisoning what counts as benign moves the threshold. Encrypted
payloads remove the content features (`failed_logins`, `num_root`) that r2l and u2r
detection leans on hardest — and those are already the weakest classes here.

**False-positive cost.** At 0.0425 FPR — 4.25% of benign flows — a link carrying
10,000 benign flows a minute generates roughly 425 false alerts a minute. No analyst reads that. Ranking is the
mitigation that exists (precision@2,000 = 1.000, critical-band precision 0.9762);
incident aggregation, which is what would actually fix it, does not — see below.

**Scalability.** Detection is stateless per flow given the model, so it shards
horizontally. The window features are the constraint: they need ordered, per-host
state, so sharding must be by host key, not round-robin.

## Limitations, stated plainly

1. **Alerts are per flow, not per incident.** `neptune` alone produced 4,656 alerts —
   45.2% of the whole queue — and the DoS class as a whole is 65.3% of it, spread
   over 169 distinct alert signatures at roughly 40 alerts each. Correlating alerts
   that share a source, destination and window into one incident is the single
   highest-value fix and it is not implemented.
2. **`r2l` detection collapses, and that is the headline failure here.** Hybrid
   recall on the 2,887 `r2l` test connections is 0.2553, and the multiclass recall for
   the class is 0.054: `guess_passwd` 0.008 over 1,231 rows, `snmpguess` and
   `snmpgetattack` 0.000 over 331 and 178. A successful password guess is one short
   authenticated session on an ordinary service; at connection-record granularity it
   is not distinguishable from a legitimate login, so no threshold over these features
   separates them. This is a feature-space limit, not a tuning one.
3. **Two rules are not carrying their weight.** R09 fires 5 times at 0.400 precision
   and R04 100 times at 0.480; R11 sits at 0.661 over 56 fires. They are reported
   rather than quietly deleted, because a rule set you have not measured is a
   liability. R05 (`land`) fires exactly 7 times, on all 7 `land` connections in the
   test file — a rule that is right and almost never applicable.
4. **The anomaly layer earns its place on accuracy and loses it on cost.** It adds
   +0.023 F1 over `signatures ∨ supervised` (477 more detections for 28 more false
   positives), which is a real gain, but it consumes 91% of detection time to do it. A
   production build would keep it and move it off the hot path — sampled, batched, or
   sharded — rather than drop it.
5. **Corroboration is a ranking signal, not a guarantee.** 187 of the 413 false
   positives are backed by two or more layers and 74 by all three, so the highest
   band still contains 173 wrong answers. The queue order is honest about
   *uncorroborated* evidence; it cannot flag confidently-agreed mistakes.
6. **Attribution is weaker than detection.** Binary accuracy is 0.8511 but multiclass
   accuracy is 0.7660 and macro-F1 0.5646; 1,515 `dos` connections are called
   `normal`, 476 `probe` connections likewise, and category attribution follows the
   highest-severity rule that matched, which mislabels the very first alert in the
   transcript above (`satan` reported as `dos`). Getting the alert is not the same as
   getting the story right.
7. **The pcap path detects the ICMP sweep but cannot name it.** All 40 sweep flows are
   flagged, yet no rule matches any of them and they rank `low`: the `dst_host_*`
   features summarise behaviour per destination, and a one-echo-per-host sweep leaves
   that history empty. It needs a cross-host aggregate feature to be ranked properly.
8. **NSL-KDD is a 1999-derived schema, and this is one split.** The corpus is the real
   benchmark, but the traffic is not modern — `service` vocabularies and attack
   families are historical, and every figure here comes from the single official
   train/test split with no cross-validation and no confidence intervals.

## Deliverables

| what | where |
|---|---|
| technical report (Markdown, 1,988 prose words) | `docs/REPORT.md` |
| technical report (Word) | `REPORT.docx` |
| video narration script (1,410 spoken words, 9:24 at 150 wpm) | `docs/VIDEO_SCRIPT.md` |
| slide deck (15 slides, the same 9:24 in the speaker notes) | `AI-NIDS-slides.pptx` / `.pdf` |
| working prototype (CLI) | `python -m nids …` |
| working prototype (visual) | `artifacts/dashboard.html` |
| every number quoted anywhere | `artifacts/evaluation.json`, `artifacts/scenarios.json` |

The deck and the docx are both generated by committed scripts
(`scripts/build_slides.py`, `scripts/build_report_docx.py`) rather than hand-made, so
they cannot drift out of step with `artifacts/figures/`. The narration is a third
generated artefact: `scripts/narration.py` holds the spoken text, `build_slides.py`
copies it into the speaker notes, `build_video_script.py` writes `docs/VIDEO_SCRIPT.md`
with timings computed from the word counts, and `tests/test_narration.py` fails if any
of the three disagree or if the run leaves the brief's 8-10 minute window.
